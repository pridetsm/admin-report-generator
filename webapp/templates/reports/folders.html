How to read this

How long the oldest file has been waiting in each watched folder. A folder that stops draining is a consumer that has stopped running.

Each folder is coloured by how long its oldest file has been waiting. The number on the folder tab is how many files are waiting in total; the figure underneath is the age of the oldest one, and processed is how many files have left the folder since midnight — messages consumed by T24 on an inbound folder, or collected by the interface on an outbound one. It empties at 00:00 and fills through the working day, so first thing in the morning a low number is the new day, not a fault. Read together with the waiting count it says whether a queue is deep because it is busy or because it has stopped: a folder that has handled hundreds today with two waiting is healthy; the same two waiting with nothing processed is jammed.

The line under each folder is the message path — where what is sitting in it came from and where it is going, so a stuck folder names the flow that has stopped rather than just a directory. T24 and RTGS only speak through the SWIFT Alliance translation layer, so those legs read RTGS → SWIFT → T24; PAYNET and EFIN feed T24 directly and show two stops, not an invented hop. The badge on the tab is the message format: MT and MX folders are the same leg of the same path and would otherwise be indistinguishable. The filter box searches paths too, so typing rtgs narrows to that flow.

Grey is healthy. An empty interface folder means everything drained, which is the normal steady state. Green means files are waiting and all of them are fresh — work in progress. Amber means the oldest has passed {{ fw.amber_text }} and the folder is drifting. Red means it has passed {{ fw.red_text }}: the folder is not busy, it is jammed, and the consumer that should be draining it has almost certainly stopped. These are payment queues — a message that has sat that long has missed its window.

Dashed and faded is neither good nor bad — it means we are not being told. Either the path could not be found on the host, the scan reported an error or was cut short, the folder has not been scanned in the last {{ fw.stale_after }} seconds, or the exporter is not answering at all. Prometheus keeps serving the last values it saw, so a stopped exporter would otherwise read as a set of permanently perfect folders. It is called out rather than coloured in.

The page updates itself. Every ten seconds it asks for fresh figures and repaints in place — there is no page refresh, and nothing here needs one. The clock at the top counts those ten seconds down and the grid ripples each time they land, so a glance tells you a refresh has just happened or how long until the next. If that number keeps climbing instead of resetting, this screen has lost the server, and the live heartbeat in the toolbar turns red with it.

That is a different question from whether the readings are current, which is judged per folder: a folder the exporter has stopped scanning turns dashed and lands under Unknown on its own, no matter how healthy the header looks.

The exporter publishes each folder's oldest file as a timestamp, not an age, so this page ages it once a second from a fixed point — a folder crosses into red the moment it truly does, not at the next scan. Open any folder for the full detail: total waiting, how many are past each limit, the size on disk, and when a file last arrived.

The two limits are set in reports/folders.py (AMBER_SECONDS / RED_SECONDS, with per-folder overrides). The exporter publishes raw ages and counts rather than a verdict, because the same numbers also feed the Prometheus alert rules and Grafana, which need the facts rather than this screen's opinion of them.
