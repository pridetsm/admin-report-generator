Busiest interfaces — throughput over the last {{ n.rate_window }}

Top {{ n.top_n }} of {{ n.carrying_count }} interfaces carrying traffic. Bars are scaled so the longest is the heaviest single direction shown — a relative scale, not a share of link capacity.

These figures are a floor, not a measurement. Only the 32-bit ifInOctets/ifOutOctets counters are polled. A 32-bit octet counter holds 4.29 GB and then rolls over. The busiest port on this switch is currently running {{ n.peak_bps_text }}, which exhausts that counter {% if n.wrap_seconds %}in about {{ n.wrap_seconds }} seconds{% else %} quickly under load{% endif %}. Prometheus scrapes this job every {{ n.scrape_interval_s }} seconds, so on that port the counter rolls over roughly every {{ n.wraps_per_scrapes }} scrapes — and every rollover loses traffic. rate() handles a rollover the only way it can: it sees the value drop, assumes the counter restarted at zero, and discards everything the counter held above that point. Worse, if enough traffic passes that the counter lands higher than where it started, there is no drop to see and a full 4.29 GB vanishes with nothing to signal it. This is not an edge case at {{ n.peak_bps_text }}; it is the normal state of that port. The 64-bit ifHCInOctets/ifHCOutOctets counters the admins asked for exist precisely to remove this, and are not yet being polled. No percentage utilisation appears anywhere in this report because ifHighSpeed is not collected, so there is no capacity to compare against.
